# Online relay protocol v1

The desktop client uses HTTPS and a JSON WebSocket at `/ws`. For development only, HTTP/WS loopback addresses are permitted. All JSON uses camelCase. IDs are UUID strings. Every command has `type` and `requestId`; replies are `{type:"response",requestId,ok,data}` or `{type:"response",requestId,ok:false,error}`. Events are `{type,data}`. Protocol version is 1.

`POST /v1/register` with `{displayName}` returns `{userId,token,friendCode,displayName}`. The opaque `d1` device token is HMAC-signed with the relay's stable `IDENTITY_SECRET`, binding the user's ID and friend code. It remains verifiable if the free service loses its files. The desktop protects it at rest. HTTP authorization is `Bearer <token>` with `X-User-Id: <userId>`. WebSocket `auth` carries `{protocol:1,userId,token,displayName,friendReceipts:[...opaque strings]}` and returns the friends snapshot. Subsequent commands require authentication.

Friends snapshot: `{user:{userId,displayName,friendCode},friends:[{userId,displayName,friendCode,online}],incoming:[...profiles],outgoing:[...profiles],friendReceipts:[...opaque strings]}`. `heartbeat` returns `{serverTime}` and keeps an authenticated desktop session active; clients send it every 60 seconds while connected. `friends.list`, `friends.request` (`friendCode`), `friends.accept` (`userId`), and `friends.remove` (`userId`) return this snapshot. Changes and presence emit `friends.changed` containing a snapshot. Explicit acceptance issues an `f1` signed receipt naming both public profiles and a unique acceptance. Each desktop saves the authoritative receipt list with its protected credential before reporting success. Maximum 256 receipts, 2048 characters each. Receipts do not contain device bearer tokens.

`collab.create` (`project`) returns `{sessionId,revision:0,project,members:[...profiles]}`. `collab.invite` (`sessionId,userId`) invites an accepted friend of the host; `collab.invite` event contains `{sessionId,from:profile,mapName}`. `collab.join` (`sessionId`) requires an invitation and accepted friendship and returns the session snapshot. `collab.members` event carries `{sessionId,members}`. Each user belongs to at most one session. `collab.leave` leaves it; host departure closes the session, emitting `collab.ended` with `{sessionId,message}`.

`collab.delta` (`sessionId,delta`) applies the existing MapDelta in relay order to the room snapshot, returns `{revision}`, and broadcasts `collab.delta` with `{sessionId,revision,delta,authorId}` to all members including the author. `collab.project` (`sessionId,project,baseRevision`) replaces the document only if the revision matches, returning `{revision}` and broadcasting `collab.project` with `{sessionId,revision,project,authorId}`. `collab.sync` (`sessionId`) returns the current session snapshot. `collab.cursor` (`sessionId,x,y`) broadcasts `{sessionId,userId,displayName,x,y}` as `collab.cursor` to other members. Projects and deltas use the existing .NET camelCase JSON representation, including base64 byte masks and numeric elevation arrays.

Game matchmaking rooms are transient and use the authenticated WebSocket. `game.rooms.list` returns `{rooms:[...]}`. A room contains `{roomId,name,host,visibility,maxPlayers,members,relayPort}`; `visibility` is `friends` or `public`, `maxPlayers` is 2–8, and each member is `{profile,relayPort}`. The relay port is a room-local route ID, not a network port open on the relay host. Public rooms appear to all connected profiles. Friends-only rooms appear to their host, accepted friends, and invitees.

`game.create` (`name,visibility,maxPlayers`) creates a room with the authenticated user as host. `game.invite` (`roomId,userId`) is host-only and requires an accepted online friend; each invitation reserves a room slot, and the recipient receives `game.invite` with `{roomId,from,name}`. `game.join` (`roomId`) permits a public room or a friends-only room invitation from an accepted friend and returns the room snapshot. `game.members` carries `{roomId,members}` after membership changes. `game.leave` leaves the current room; host departure ends it with `game.ended`. Removing a friendship revokes any room invitation and removes the other friend from that host's room. Rooms close on relay restart or host disconnect.

`game.signal` (`roomId,targetUserId,signalType,payload`) forwards one ICE offer, answer, or candidate to another online room member. Both sender and recipient must be current room members. The relay limits a signal to 16 KiB and applies per-socket rate limits. It does not accept WebSocket binary gameplay frames.

After room membership changes, each client creates a direct WebRTC peer connection to every other member. The lower user UUID creates the offer so both clients agree on who negotiates. ICE signaling travels through the authenticated WebSocket, and ICE uses the public STUN server `stun:stun.l.google.com:19302` to discover reachable addresses. The peers open an unordered, unreliable `edmw-game-udp` data channel for game datagrams and an ordered, reliable `edmw-game-tcp` data channel for game TCP streams. The relay carries no gameplay bytes and does not provide TURN or a gameplay fallback. A restrictive firewall or NAT can prevent a direct path; in that case the game connection fails and the UI reports that direct ICE could not connect.

On the UDP data channel, each app frame is `EDGU` (4 ASCII bytes), source game port (unsigned 16-bit big-endian), target game port (unsigned 16-bit big-endian), and 1–1200 payload bytes. For room broadcasts, the sender sends a copy to each direct peer. The x86 `EDMWRelayBridge.dll` hooks the supported `TCP Protocol.dll` Winsock imports inside the launched game process; received datagrams are injected through a local UDP socket and restore the sender's virtual address in `10.254.255.1`–`10.254.255.8`, mapped to room route IDs `40000`–`40007`.

The native hook redirects provider TCP connects to a local Mod Studio proxy. The app opens the matching game TCP listener locally, then copies stream frames over the reliable direct data channel. Each TCP frame has a 25-byte header: `EDWT`, a 16-byte stream ID, source and target game ports (unsigned 16-bit big-endian), and a one-byte type (`1` open, `2` accepted, `3` data, `4` closed, `5` rejected), followed by up to 1100 data bytes. The hook and helper are extracted under local app data and injected only for this launch; game installation files are not replaced.

The launcher checks the supported `Empires_DMW.exe` and `TCP Protocol.dll` SHA-256 identities before starting. After joining a room, choose **Launch EDMW** in Matchmaking, then host or join through the game's TCP/IP LAN screen. Everyone needs the same game/provider build and matching gameplay data. Live cross-internet session validation has not yet been completed.

`export.offer` (`userId,kind,name,size,sha256`) requires an online accepted friend; kind is `map` or `civilization`. It returns `{exportId}`. `PUT /v1/exports/<exportId>` uploads the exact bytes (map archive or CivilizationInstallerPackageCodec data) with the sender's HTTP authorization. The relay verifies size and SHA-256 before emitting `export.offer` to the recipient with `{exportId,from:profile,kind,name,size,sha256}`. Only that recipient may `GET /v1/exports/<exportId>`. `export.decide` (`exportId,status,message`) accepts statuses `installed`, `denied`, or `failed`; the relay forwards `export.result` `{exportId,status,message}` to the sender and deletes the package. Offers expire after 10 minutes; the relay emits a failed result and deletes their bytes. Removal of a friendship revokes invites, participation, and pending exports. Payload limit is 128 MiB; map payload limit is 32 MiB. The recipient validates package contents and asks for installation approval through existing review dialogs.

On recovery, a signed device token recreates its original user ID and friend code. Each authenticated device declares its current accepted receipts. A one-sided receipt may retain an offline contact but cannot authorize sharing; active restoration requires both devices to declare the same valid acceptance. A known peer's omission clears stale counterpart claims. Removal clears saved receipts and revokes participation/transfers. If an explicit acceptance happened while the requester was offline, the current relay can deliver that receipt on their next connection; losing the filesystem before delivery requires a new request. Sessions, pending requests, and exports are transient. Render's free plan uses no disk or external database; keep `IDENTITY_SECRET` stable. Run one instance until shared state and distributed routing are implemented.

`export.cancel` (`exportId`) is sender-only and withdraws a pending offer. Revocation, expiry, withdrawal, or a participant disconnect emits `export.cancelled` to the recipient, cancels their outstanding review token, and reports a failed `export.result` to the sender where connected. Both upload and download streams are aborted and temporary bytes deleted. Client command response callbacks register export result waiters in receive order so an immediate revocation cannot race the registration.
