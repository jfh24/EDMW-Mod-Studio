# Online relay protocol v1

The desktop client uses HTTPS and a JSON WebSocket at `/ws`. For development only, HTTP/WS loopback addresses are permitted. All JSON uses camelCase. IDs are UUID strings. Every command has `type` and `requestId`; replies are `{type:"response",requestId,ok,data}` or `{type:"response",requestId,ok:false,error}`. Events are `{type,data}`. Protocol version is 1.

`POST /v1/register` with `{displayName}` returns `{userId,token,friendCode,displayName}`. The opaque `d1` device token is HMAC-signed with the relay's stable `IDENTITY_SECRET`, binding the user's ID and friend code. It remains verifiable if the free service loses its files. The desktop protects it at rest. HTTP authorization is `Bearer <token>` with `X-User-Id: <userId>`. WebSocket `auth` carries `{protocol:1,userId,token,displayName,friendReceipts:[...opaque strings]}` and returns the friends snapshot. Subsequent commands require authentication.

Friends snapshot: `{user:{userId,displayName,friendCode},friends:[{userId,displayName,friendCode,online}],incoming:[...profiles],outgoing:[...profiles],friendReceipts:[...opaque strings]}`. `heartbeat` returns `{serverTime}` and keeps an authenticated desktop session active; clients send it every 60 seconds while connected. `friends.list`, `friends.request` (`friendCode`), `friends.accept` (`userId`), and `friends.remove` (`userId`) return this snapshot. Changes and presence emit `friends.changed` containing a snapshot. Explicit acceptance issues an `f1` signed receipt naming both public profiles and a unique acceptance. Each desktop saves the authoritative receipt list with its protected credential before reporting success. Maximum 256 receipts, 2048 characters each. Receipts do not contain device bearer tokens.

`collab.create` (`project`) returns `{sessionId,revision:0,project,members:[...profiles]}`. `collab.invite` (`sessionId,userId`) invites an accepted friend of the host; `collab.invite` event contains `{sessionId,from:profile,mapName}`. `collab.join` (`sessionId`) requires an invitation and accepted friendship and returns the session snapshot. `collab.members` event carries `{sessionId,members}`. Each user belongs to at most one session. `collab.leave` leaves it; host departure closes the session, emitting `collab.ended` with `{sessionId,message}`.

`collab.delta` (`sessionId,delta`) applies the existing MapDelta in relay order to the room snapshot, returns `{revision}`, and broadcasts `collab.delta` with `{sessionId,revision,delta,authorId}` to all members including the author. `collab.project` (`sessionId,project,baseRevision`) replaces the document only if the revision matches, returning `{revision}` and broadcasting `collab.project` with `{sessionId,revision,project,authorId}`. `collab.sync` (`sessionId`) returns the current session snapshot. `collab.cursor` (`sessionId,x,y`) broadcasts `{sessionId,userId,displayName,x,y}` as `collab.cursor` to other members. Projects and deltas use the existing .NET camelCase JSON representation, including base64 byte masks and numeric elevation arrays.

Game matchmaking rooms are transient and use the authenticated WebSocket. `game.rooms.list` returns `{rooms:[...]}`. A room contains `{roomId,name,host,visibility,maxPlayers,members,relayPort,gameHostUserId}`; `visibility` is `friends` or `public`, `maxPlayers` is 2–8, and each member is `{profile,relayPort}`. The relay port is a room-local route ID, not a network port open on the relay host. Public rooms appear to all connected profiles. Friends-only rooms appear to their host, accepted friends, and invitees. This is why a hosted room appears to other users when it was created as public. ICE signaling requires both peers to be current members of the same room, and game broadcast packets are forwarded only to that room's members; room-list visibility does not expose gameplay traffic across rooms. `gameHostUserId` identifies the member hosting EDMW and defaults to the matchmaking room host; the host may designate another current member.

`game.create` (`name,visibility,maxPlayers`) creates a room with the authenticated user as host. `game.invite` (`roomId,userId`) is host-only and requires an accepted online friend; each invitation reserves a room slot, and the recipient receives `game.invite` with `{roomId,from,name}`. `game.join` (`roomId`) permits a public room or a friends-only room invitation from an accepted friend and returns the room snapshot. The matchmaking host can designate a current member with `game.host.set` (`userId`); the relay broadcasts `game.members` with both the updated member list and `gameHostUserId`. The designation clears if that member leaves. `game.leave` leaves the current room; host departure ends it with `game.ended`. Removing a friendship revokes any room invitation and removes the other friend from that host's room. Rooms close on relay restart or host disconnect.

`game.signal` (`roomId,targetUserId,signalType,payload`) forwards one ICE offer, answer, or candidate to another online room member. Both sender and recipient must be current room members. The relay limits a signal to 16 KiB and applies per-socket rate limits.

After room membership changes, each client creates a direct WebRTC peer connection to every other member. The lower user UUID creates the offer so both clients agree on who negotiates. ICE signaling travels through the authenticated WebSocket, and ICE uses the public STUN server `stun:stun.l.google.com:19302` to discover reachable addresses. Direct peers open an unordered, unreliable `edmw-game-udp` data channel for game datagrams and an ordered, reliable `edmw-game-tcp` data channel for game TCP streams. The client uses direct channels when they are open. If direct ICE or a particular data channel is unavailable, that peer's gameplay and session-control frames are sent over the existing authenticated WebSocket instead. This room-scoped relay fallback is not TURN and does not require inbound port forwarding. It adds relay latency and consumes relay bandwidth; it can still fail if the matchmaking WebSocket is unavailable or the relay's rate/backpressure limits are reached.

Binary WebSocket gameplay frames use the `EDMR` magic. A client-to-relay frame has a 23-byte header: `EDMR` (4 ASCII bytes), type (1 byte: `1` UDP, `2` TCP, `3` session control), room ID (16 UUID bytes in network order), and destination relay port (unsigned 16-bit big-endian). The relay accepts a frame only from the authenticated connection's current room member, checks its type and size, and routes it to the destination member's assigned relay port. UDP destination port `0` broadcasts to all other room members. The relay adds a 16-byte sender user ID after the room ID in server-to-client frames, making the returned header 37 bytes. Clients verify the room and sender against current room membership before accepting a frame. Per-client limits are 2048 gameplay frames and 2 MiB of input per second; recipients with more than 2 MiB buffered are closed to bound memory.

UDP relay payload is source game port (unsigned 16-bit big-endian), target game port (unsigned 16-bit big-endian), and 1–1200 datagram bytes. TCP relay payload is one existing `EDWT` frame. Session-control relay payload is an opaque 1–16 KiB frame. WebSocket transport encryption protects traffic in transit, but the relay can read forwarded game frames; the protocol does not implement end-to-end encryption.

On the direct UDP data channel, each app frame is `EDGU` (4 ASCII bytes), source game port (unsigned 16-bit big-endian), target game port (unsigned 16-bit big-endian), and 1–1200 payload bytes. When a direct channel is unavailable, the same game datagram is wrapped in an `EDMR` UDP frame and forwarded by the relay. For room broadcasts, the sender sends a copy to each direct peer or relay destination. The x86 `EDMWRelayBridge.dll` hooks the supported `TCP Protocol.dll` Winsock imports inside the launched game process; received datagrams are injected through a local UDP socket and restore the sender's virtual address in `10.254.255.1`–`10.254.255.8`, mapped to room route IDs `40000`–`40007`. The bridge prefers the local IPv4 address from ICE's selected host/base candidate; for server-reflexive candidates it uses `raddr`, not the public STUN-mapped address. If ICE selects an IPv6 route, the bridge falls back to the highest-priority gathered local IPv4 host/base candidate because EDMW's provider requires IPv4. If ICE has not provided a local address, it uses Windows' active default-route IPv4 adapter. A reflexive candidate without `raddr` is never treated as a local adapter address. The bridge rewrites only the matching address in `GetAdaptersInfo` and matching `dwForwardDest` and `dwForwardNextHop` values returned by `GetIpForwardTable`. Other adapter addresses remain intact. The virtual address is the game-level route shown in Matchmaking; it is not an ICE/STUN candidate address.

The native hook redirects provider TCP connects to a local Mod Studio proxy. The app opens the matching game TCP listener locally, then copies stream frames over the reliable direct data channel or WSS fallback. Each TCP frame has a 25-byte header: `EDWT`, a 16-byte stream ID, source and target game ports (unsigned 16-bit big-endian), and a one-byte type (`1` open, `2` accepted, `3` data, `4` closed, `5` rejected), followed by up to 1100 data bytes. The hook and helper are extracted under local app data and injected only for this launch; game installation files are not replaced.

The launcher checks the supported `Empires_DMW.exe` and `TCP Protocol.dll` SHA-256 identities before starting. Headless two-client loopback verification covers bidirectional UDP, TCP, and control traffic through WSS. A real two-PC cross-internet game test has not yet been completed.

### Room game setup

The Matchmaking panel's **Prepare game network** action requires a connected room relay and usable local IPv4 mapping, then launches the supported game executable at its native UI for each player. Mod Studio configures each player's virtual room address and runs the address and route-table hooks while EDMW uses its own multiplayer UI. Direct ICE is preferred, and the authenticated WSS path carries game traffic for peers without a direct route. The designated host creates the game in EDMW; other players select Join by IP and enter the host's virtual address shown in Matchmaking (or copy it with **Copy host IP**). Players then use the game's UI to start the map. Status reports direct ICE state, whether WSS gameplay traffic is active, and network setup. Headless loopback verification passes; live cross-internet game validation remains pending.

`export.offer` (`userId,kind,name,size,sha256`) requires an online accepted friend; kind is `map` or `civilization`. It returns `{exportId}`. `PUT /v1/exports/<exportId>` uploads the exact bytes (map archive or CivilizationInstallerPackageCodec data) with the sender's HTTP authorization. The relay verifies size and SHA-256 before emitting `export.offer` to the recipient with `{exportId,from:profile,kind,name,size,sha256}`. Only that recipient may `GET /v1/exports/<exportId>`. `export.decide` (`exportId,status,message`) accepts statuses `installed`, `denied`, or `failed`; the relay forwards `export.result` `{exportId,status,message}` to the sender and deletes the package. Offers expire after 10 minutes; the relay emits a failed result and deletes their bytes. Removal of a friendship revokes invites, participation, and pending exports. Payload limit is 128 MiB; map payload limit is 32 MiB. The recipient validates package contents and asks for installation approval through existing review dialogs.

On recovery, a signed device token recreates its original user ID and friend code. Each authenticated device declares its current accepted receipts. A one-sided receipt may retain an offline contact but cannot authorize sharing; active restoration requires both devices to declare the same valid acceptance. A known peer's omission clears stale counterpart claims. Removal clears saved receipts and revokes participation/transfers. If an explicit acceptance happened while the requester was offline, the current relay can deliver that receipt on their next connection; losing the filesystem before delivery requires a new request. Sessions, pending requests, and exports are transient. Render's free plan uses no disk or external database; keep `IDENTITY_SECRET` stable. Run one instance until shared state and distributed routing are implemented.

`export.cancel` (`exportId`) is sender-only and withdraws a pending offer. Revocation, expiry, withdrawal, or a participant disconnect emits `export.cancelled` to the recipient, cancels their outstanding review token, and reports a failed `export.result` to the sender where connected. Both upload and download streams are aborted and temporary bytes deleted. Client command response callbacks register export result waiters in receive order so an immediate revocation cannot race the registration.
