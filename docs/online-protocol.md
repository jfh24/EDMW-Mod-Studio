# Online relay protocol v1

The desktop client uses HTTPS and a JSON WebSocket at `/ws`. For development only, HTTP/WS loopback addresses are permitted. All JSON uses camelCase. IDs are UUID strings. Every command has `type` and `requestId`; replies are `{type:"response",requestId,ok,data}` or `{type:"response",requestId,ok:false,error}`. Events are `{type,data}`. Protocol version is 1.

`POST /v1/register` with `{displayName}` returns `{userId,token,friendCode,displayName}`. A random device credential identifies the user. The desktop protects it at rest. HTTP authorization is `Bearer <token>` with `X-User-Id: <userId>`. WebSocket `auth` carries `{protocol:1,userId,token,displayName}` and returns the friends snapshot. Subsequent commands require authentication.

Friends snapshot: `{user:{userId,displayName,friendCode},friends:[{userId,displayName,friendCode,online}],incoming:[...profiles],outgoing:[...profiles]}`. `friends.list`, `friends.request` (`friendCode`), `friends.accept` (`userId`), and `friends.remove` (`userId`) return this snapshot. Changes and presence emit `friends.changed` containing a snapshot. Relationships become friendships only through explicit acceptance.

`collab.create` (`project`) returns `{sessionId,revision:0,project,members:[...profiles]}`. `collab.invite` (`sessionId,userId`) invites an accepted friend of the host; `collab.invite` event contains `{sessionId,from:profile,mapName}`. `collab.join` (`sessionId`) requires an invitation and accepted friendship and returns the session snapshot. `collab.members` event carries `{sessionId,members}`. Each user belongs to at most one session. `collab.leave` leaves it; host departure closes the session, emitting `collab.ended` with `{sessionId,message}`.

`collab.delta` (`sessionId,delta`) applies the existing MapDelta in relay order to the room snapshot, returns `{revision}`, and broadcasts `collab.delta` with `{sessionId,revision,delta,authorId}` to all members including the author. `collab.project` (`sessionId,project,baseRevision`) replaces the document only if the revision matches, returning `{revision}` and broadcasting `collab.project` with `{sessionId,revision,project,authorId}`. `collab.sync` (`sessionId`) returns the current session snapshot. `collab.cursor` (`sessionId,x,y`) broadcasts `{sessionId,userId,displayName,x,y}` as `collab.cursor` to other members. Projects and deltas use the existing .NET camelCase JSON representation, including base64 byte masks and numeric elevation arrays.

`export.offer` (`userId,kind,name,size,sha256`) requires an online accepted friend; kind is `map` or `civilization`. It returns `{exportId}`. `PUT /v1/exports/<exportId>` uploads the exact bytes (map archive or CivilizationInstallerPackageCodec data) with the sender's HTTP authorization. The relay verifies size and SHA-256 before emitting `export.offer` to the recipient with `{exportId,from:profile,kind,name,size,sha256}`. Only that recipient may `GET /v1/exports/<exportId>`. `export.decide` (`exportId,status,message`) accepts statuses `installed`, `denied`, or `failed`; the relay forwards `export.result` `{exportId,status,message}` to the sender and deletes the package. Offers expire after 10 minutes; the relay emits a failed result and deletes their bytes. Removal of a friendship revokes invites, participation, and pending exports. Payload limit is 128 MiB; map payload limit is 32 MiB. The recipient validates package contents and asks for installation approval through existing review dialogs.

Friend identities and relationships persist in the relay data directory. Sessions and export offers are transient, and clients explicitly reconnect after a relay restart. A Render persistent disk is required for durable identities. Run one relay instance until shared storage and distributed room routing are implemented.

`export.cancel` (`exportId`) is sender-only and withdraws a pending offer. Revocation, expiry, withdrawal, or a participant disconnect emits `export.cancelled` to the recipient, cancels their outstanding review token, and reports a failed `export.result` to the sender where connected. Both upload and download streams are aborted and temporary bytes deleted. Client command response callbacks register export result waiters in receive order so an immediate revocation cannot race the registration.
